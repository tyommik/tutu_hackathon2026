# Предложения к Tutu MCP

Находки из живой работы с https://mcp.tutu.ru/mcp. Формат: находка → как это
бьёт по агентам → предложение. Каждая находка воспроизводима, рядом — место
в нашем коде, где грабля обойдена.

## 1. `search_multitransport` не строит составные маршруты

**Находка.** Инструмент параллельно опрашивает avia/rail/bus/etrain на одну
пару городов; цепочку «малый город → хаб → заграница» он не соберёт.
**Влияние.** Любой агент, планирующий реальное путешествие, обязан сам
раскладывать маршрут на плечи, сам подбирать пересадки и сам следить за
стыковками — это самая дорогая часть работы (у нас: `src/lib/transfers.ts`,
`src/lib/repair.ts`).
**Предложение.** Инструмент составных маршрутов (origin, destination, via?)
или хотя бы подсказка хабов в ответе пустого поиска.

## 2. Пустая выдача без причины

**Находка.** Ноль офферов выглядит одинаково для «рейсов нет», «продажи ещё
не открыты» (у РЖД горизонт ~90 дней) и «город не тот» (см. п. 3).
**Влияние.** Агент не может объяснить пользователю, что делать: ждать
открытия продаж, менять дату или чинить город. Мы восстанавливаем причины
эвристиками (`src/lib/emptyReasons.ts`).
**Предложение.** Поле `empty_reason` в ответе поиска: `no_service` /
`sales_not_open` (+ дата открытия) / `no_offers_for_date`.

## 3. Геокодер разрешает «Бали» в город с IATA BLC

**Находка.** Запрос «Бали» находит одноимённый город (Камерун) и честно
отдаёт ноль рейсов; резолв не виден в ответе.
**Влияние.** Агент получает пустоту и не знает, что искал не то место.
Мы держим словарь алиасов «Бали → Денпасар» (`src/lib/geoAliases.ts`) и
показываем пользователю «как Туту понял город» из `meta` поиска.
**Предложение.** Возвращать resolved-гео (название, страна, IATA) первым
классом в каждом ответе поиска + принимать популярные топонимы-регионы.

## 4. Цены за партию и за место — в одних и тех же полях

**Находка.** Авиа отдаёт цену за всю партию пассажиров, ж/д — за место.
Поле называется одинаково, признака нет.
**Влияние.** Бюджет маршрута на семью сравнивает несравнимое; мы напоролись
на это при составе 3+ человека (нормализация — `src/lib/search.ts`).
**Предложение.** Явное поле `price_scope: party | seat` или единая семантика.

## 5. Пассажирские параметры у инструментов разные

**Находка.** `search_rail` принимает только `passengers`, авиа — взрослых и
возрасты детей, отели — своё; `search_rail` ждёт `departure_date`, а не
`date`, как соседи.
**Влияние.** У каждого агента появляется слой-переводчик (наш `paxArgs()` в
`src/lib/search.ts`); ошибки в нём — тихие неверные цены.
**Предложение.** Единый контракт `party {adults, children_ages[]}` и единые
имена дат во всех инструментах поиска.

## 6. `mtp-deeplink.tutu.ru` отдаёт 401 вне браузера

**Находка.** Ссылки из `create_checkout_link` на curl/HEAD отвечают 401
(бот-защита), проверяемы только в браузере.
**Влияние.** Агент не может автоматически верифицировать главный артефакт —
ссылку на оплату; наш checkout полагается на статус создания ссылки.
**Предложение.** Лёгкий эндпоинт валидации ссылки (или исключение для HEAD).

## 7. `get_rail_seatmap` с `view='full'` — недокументированная жемчужина

**Находка.** Параметр `view='full'` отдаёт геометрию мест (position, size) —
из ответа рисуется настоящая схема вагона (наш `SeatmapModal`).
**Влияние.** Без документации фичу находят случайно.
**Предложение.** Задокументировать и закрепить контракт геометрии.

## 8. Session-less вызовы работают, но контракт не описан

**Находка.** `tools/call` по streamable HTTP отвечает без
initialize-handshake (наш `src/lib/mcp.ts` этим живёт — меньше состояния).
**Влияние.** Непонятно, можно ли на это опираться: поведение может пропасть
при обновлении сервера.
**Предложение.** Явно задокументировать поддерживаемый режим.

## 9. Отель без цены в выдаче

**Находка.** `best_offer` у части отелей приходит без цены.
**Влияние.** Сортировки «от дешёвых» и бюджетная логика агента спотыкаются;
у нас такие отели не участвуют в «от N ₽» (`src/lib/activityLog.ts`,
`src/store/useTrip.ts`).
**Предложение.** Либо всегда цена, либо явный флаг `price_unavailable`.

## 10. Долгие поиски без прогресса

**Находка.** Поиск на плечо занимает единицы—десятки секунд, ответ приходит
целиком; составной подбор пересадки — минуты.
**Влияние.** Агент не может показывать честный прогресс из данных — мы
собираем его сами из завершившихся веток (журнал шагов, поле статуса).
**Предложение.** Частичные результаты / прогресс-события в streamable HTTP —
транспорт уже позволяет.
